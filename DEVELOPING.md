# Developing SEL Trip Event Analyzer

There is one program: a single web page. The Windows program is a small
launcher that shows that page in its own window.

| File | What it is |
|---|---|
| `web/core.js` | Parsing (CEV, EVE/TXT/SUM/HDR, HIS, SER, RDB), cause analysis, CHECK flags, two-ended pairs, incidents, repeat trips, the report text and CSV |
| `web/analysis.js` | Waveform maths: CEV and COMTRADE records, phasors, sequence components, harmonics, fault classification, 50/51 evaluation, element meanings |
| `web/reference.js` | The built-in reference waveforms |
| `web/docx.js` | Word (.docx) writer, no dependencies |
| `web/weather.js` | Open-Meteo geocoding and historical weather, and the weather cause hints |
| `web/wave_ui.js` | The Waveform analysis page (charts, phasor diagram, notes, exports) |
| `web/app.html` | The page: layout, summary, notes, weather, updates, desktop bridge |
| `web/cli.js` | The same analysis from the command line |
| `web/history.js` | Trip History: event records across files, issue types, recurrence, hot spots, trends, ranking, report blocks and CSV |
| `web/history_ui.js`, `web/history_ui.css` | The History screen as a module (`SELHistoryUI.mount`), scoped to `.hx` with `hx-` ids: used by the Analyzer's History tab and by `history.html`. One IndexedDB database per history (`sel-trip-history`, `sel-trip-history:<id>`), list in `localStorage` |
| `web/history.html` | The standalone Trip History page: header, theme and the mounted module |
| `web/history_cli.js` | Trip History from the command line |
| `sel_trip_analyzer.py` | Windows launcher (standard library only): local server, Edge app window, Save dialogs, file hand-off, updater |
| `scripts/build_history.py` | Builds `dist/SEL_Trip_History.html` (with `sample_history/`, made by `scripts/make_history_samples.py`) |
| `scripts/build_html.py` | Inlines everything (plus the samples and the icon) into `dist/SEL_Trip_Analyzer.html` |

All scripts work in browsers and in Node (`require("./web/core.js")`).

## Run from source

```
python scripts/build_html.py              # writes dist/SEL_Trip_Analyzer.html: open it in a browser
python sel_trip_analyzer.py [files]       # desktop window (builds the page from web/ on each start)
node web/cli.js sample_files              # report on the command line
node web/cli.js --format csv --show review sample_files
```

`web/cli.js` flags: `--show all|trips|review|faults|notrip`, `--relay NAME`,
`--sort time|newest|relay|review`, `--detail summary|standard|full`,
`--search TEXT`, `--hide-duplicates`, `--format text|csv`, `--comments TEXT`, `--now STAMP`.

## How the desktop launcher works

`sel_trip_analyzer.py` serves the page on `http://127.0.0.1:47615` (a fixed
port so the page's saved notes, locations and settings persist) and opens it
with `msedge --app=… --user-data-dir=%LOCALAPPDATA%\SEL Trip Analyzer\window`.
It injects `window.SEL_DESKTOP = {token, version}`; the page then routes
exports through `/api/save` (native Save As dialog), links through
`/api/open-url` (default browser), updates through `/api/update` and
`/api/update-install`, and polls `/api/pending` for files dropped on the icon or
handed over by a second launch (`/api/handoff`, using `instance.json`). Every
API call needs the token and a localhost `Host` header. The launcher exits when
the Edge window closes (or the page stops checking in). Without Edge or Chrome
it uses the default browser. `--selftest` checks the bundled page and API and
is run on the built exe by the release workflow.

## Tests

```
node --test "tests/*.test.js"                  # analysis, COMTRADE, reference library, Word writer, weather
python -m unittest discover -s tests -v        # desktop launcher and updater
python scripts/build_html.py && node tests/browser_test.js [screenshot-folder]   # end to end in Chromium (Playwright)
```

CI runs all three on every push (`.github/workflows/tests.yml`). The browser
test compares the page with `web/cli.js`, then drives samples, uploads, view
options, exports (txt, docx, csv, print), event notes, weather (mocked), the
Waveform analysis page (reference stepping, COMTRADE, pinned notes, zoom, Word
export), feedback, dark mode, help and the phone layout.

The expected answers come from the sample files. To lock in behaviour on
**real** relay files, run `node scripts/add_fixture.js <case-name> <files>`: it
replaces relay and station names, renames the files, refuses to write if a name
is left, and drafts `tests/fixtures/<case-name>/expected.json` for you to finish
(see `tests/fixtures/README.md`). This repo is public, so read the result once.

## Sample files

`sample_files/` is generated by `python scripts/make_samples.py` (needs
`olefile`). It also writes `SEL_sample_files.zip`, which the release workflow
attaches to each release. To change a scenario, edit the script and
regenerate; don't hand-edit the files.

## Screenshots

`node scripts/screenshots.js` (after building the page) renders
`docs/screenshots/*.png` in dark mode with Playwright. `.github/workflows/screenshots.yml`
does the same and commits them whenever the page changes on `main`.

## Building the .exe

On Windows, double-click `build_exe.bat`. It builds the page, bundles it with
PyInstaller and runs the exe's self-test. The output is `dist\SEL_Trip_Analyzer.exe`.

## Releasing

1. Bump `VERSION` in `sel_trip_analyzer.py`, write the notes in
   `docs/releases/vX.Y.Z.md`, and merge to `main`.
2. Push the tag: `git tag vX.Y.Z && git push origin vX.Y.Z`.
3. `.github/workflows/release.yml` checks the tag matches `VERSION`, runs the
   tests, builds the page, the History page, both sample zips and the `.exe` on
   Windows, self-tests the `.exe`, and publishes the release with those notes
   and files. Installed copies then offer the update.

Publishing a release by hand on GitHub (**Releases → Draft a new release**,
tag `vX.Y.Z`) still works: the same workflow builds and attaches the files.
It can also be run by hand (**Actions → Build and release → Run workflow**) to
trial-build a branch without publishing anything.

## Website

The online copy is served by GitHub Pages from the `gh-pages` branch
(Settings → Pages → Source: **Deploy from a branch**, `gh-pages`, `/ (root)`).
`.github/workflows/pages.yml` rebuilds the page and updates that branch whenever
the app changes on `main`; don't edit `gh-pages` by hand.
